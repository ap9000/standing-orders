# Native coding foundation

This change supplies the native session backend. The web workspace, chat integrations, shipping controls, and a live installation upgrade are separate work.

- Codex runs through its installed app-server with its own login, configuration, repository rules, skills, and MCP tools. Standing Orders supplies a dedicated Git checkout and frozen project knowledge/skill files. It removes inherited chat-service credentials and the invoking desktop session’s control variables.
- Sessions, transcripts, approval requests, delivery receipts, and process custody live in a separate SQLite catalog. The existing orders database schema is unchanged. Account generation and project access are rechecked before asynchronous native mutations when the caller supplies the authorization callback.
- A repeated message ID succeeds only after recorded acceptance. Rejection permits an explicit new request; pending or unknown delivery preserves the original identity. Startup saves the initial request before contacting Codex. Neither disconnection nor recovery automatically resends a message.
- Recovery checks saved process custody and the exact native conversation. If startup lost the native thread ID, verified process exit permits explicit closure while preserving the request and checkout. A prepared but unconfirmed first message likewise needs explicit review; it is never replayed.
- Native extra-access approvals route to the user. Shutdown drains pending operations, attempts native cleanup even if transcript persistence fails, and retains an uncertainty fence when cleanup cannot be proved. Historical process IDs are observation evidence, never authority to signal another process.
- Both desktop and browser deployment paths retain verified SQLite backups including committed WAL records. Coding work blocks update drain; verified native shutdown is required before replacement or restoration. Both update journals retain whether a catalog was observed. Presence is recorded before waits and rechecked before backup, replacement, restoration or reopening admission. Desktop swaps repeat worker and native quiescence after controller/signature waits, and stopped-state completion verifies final cleanup. Browser replacement retains both prepared and current service process IDs and rechecks exit after migration or rollback module loading. First late catalogs receive a consistent SQLite backup before replacement, restoration or successful release. Each boundary rechecks that retained backup as a regular, unlinked file with its recorded hash, after asynchronous work. A performed replacement is recorded and recovered from actual bundle identity after a crash; harmless pre-replacement cancellation does not require a backup. A legacy installation that never had a coding catalog remains supported.

The native agent uses installation-level credentials and tools; a project checkout is not a credential boundary and does not prevent reads outside that project. macOS process ancestry is observational, and unknown observations remain fenced. Another native client can own a thread; the adapter does not force takeover or delete lock files. Codex is the only implemented provider.

SQLite is loaded only when a database operation needs it. Importing coding session definitions or update helpers into browser enhancement modules does not load the native driver. This follows the main store’s existing runtime boundary; database operations still use Node’s real SQLite implementation.
